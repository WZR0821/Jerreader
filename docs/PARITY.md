# iOS 与 Android 的差异核对与对齐结果

核对基准：`iosApp/Jerreader`（SwiftUI）对 `ui/`＋`androidApp/`（Compose）。
版本：1.5.1 (60)，最后核对：2026-08-10。

对齐方向的默认规则：**以 iOS 的视觉为准**，因为它是这套设计语言的原稿；
但当 Android 的做法在信息量上更好时，反过来改 iOS，并在下面写明原因。

---

## 1. 已修掉的差异

### 1.1 文案：同一句话写了两遍

这是差异最大的一类，而且没有任何一处是有人决定过的——只是两边各写了一遍字符串字面量。

现在全部收进 `core/src/commonMain/kotlin/com/jerreader/unified/design/JerreaderCopy.kt`：
Compose 直接读，Swift 通过 `JerreaderCore.framework` 读同一份常量
（`JerreaderCopy.shared.libraryTitle`）。

| 位置 | 原 iOS | 原 Android | 现在 |
| --- | --- | --- | --- |
| 书架页大标题 | 书架 | **书库** | 书架 |
| 最近阅读区块标题 | 继续阅读 | **最近查看** | 继续阅读 |
| 最近阅读区块副标题 | 上次打开的书 | **继续上次阅读** | 上次打开的书 |
| 统计卡标题 | 阅读统计 | **阅读概览** | 阅读统计 |
| 统计卡副标题（有进度时） | 只记录本机阅读进度 | **每一次打开，都在向前一点** | 只记录本机阅读进度 |
| 删除确认标题 | 删除这本电子书？ | 删除《书名》？ | **删除《书名》？**（见下） |
| 删除确认正文 | …不会影响“文件”App 中的原文件。 | …不会修改原始导入文件。 | …不会影响原始导入文件。 |
| 删除确认按钮 | 删除本地副本 | **删除** | 删除本地副本 |
| 书卡菜单第一项 | 编辑书籍信息 | **管理书籍** | 编辑书籍信息 |

除表中这些原本就不一致的以外，另有一批两端**碰巧还一致**的文字也一并收了进去——
底部三个标签（书架／学习／设置）、设置页大标题、书籍信息编辑页标题「管理书籍」、
以及「保存」「取消」。它们今天相同纯属巧合，没有任何机制拦着下一次只改一边。

两处**反向对齐**（改的是 iOS）：

- **删除确认标题带书名**。iOS 问「删除这本电子书？」，Android 问「删除《动物农场》？」。
  确认框存在的意义就是不会认错书，所以留下带书名的那一版。
- **删除确认正文不再提「文件」App**。那句安慰话在一台没有「文件」App 的手机上不成立。

### 1.2 排版：书架大标题字号字重不一致

Android 的大标题用 `MaterialTheme.typography.displaySmall`，但 `jerreaderTypography`
从来没有定义过 `displaySmall`，于是落到 Material 默认的 **36sp Regular**；
iOS 的 large title 是 **34pt Bold**。这是两个书架在首屏最明显的不一样。

已在 `JerreaderTheme.kt` 显式定义 `displaySmall = 34sp / Bold`。

### 1.3 空书架插图尺寸差一圈

| | iOS `JerreaderEmptyState` | 原 Android | 现在 |
| --- | --- | --- | --- |
| 图标底板 | 68pt | 96dp | 68dp |
| 圆角 | 20pt | 24dp | 20dp |
| 字形 | 30pt | 46dp | 30dp |

Android 还缺「本机保存，不会上传」这一行，已补上。

### 1.4 书架顶栏结构不同

iOS 是 `＋` ＋ 一个 `⋯` 溢出菜单，排序和批量整理都在菜单里。
Android 原来是三个并排图标按钮（批量整理／排序／＋），而且排序按钮是「点一下换下一种」，
用户看不到当前排序是什么。

已改为与 iOS 相同的 `＋` ＋ 溢出菜单，菜单里列出三种排序（当前项显示为
「排序方式：最近」）和「批量整理书籍」。

### 1.5 文件夹的呈现方式完全不同

iOS 用横向滚动的**文件夹卡片**（132pt 最小宽 × 64pt 高，14pt 圆角，
未选中时 0.75pt 描边），每张卡显示文件夹名和「N 本」。
Android 用的是一排 Material `FilterChip`——能用，但 chip 放不下计数，
所以两边对「文件夹长什么样」的理解根本不一致。

已在 `LibraryComponents.kt` 新增 `LibraryFolderSection`，按 Swift 源码的几何值实现；
为此给 `JerreaderIcon` 加了 `FOLDER` 字形。

### 1.6 区块顺序不同

iOS：继续阅读 → 文件夹 → 所有书籍 → **阅读统计（页尾）**。
Android：**阅读统计（页首）** → 最近查看 → 所有书籍。

已按 iOS 调整。统计是对下面这些书的总结，放在它总结的东西上面本来就不对。

### 1.7 搜索/筛选结果为空时没有反馈

iOS 有 `ContentUnavailableView`「没有匹配的书籍 / 请清除搜索文字或切换文件夹。」
Android 直接渲染一个空网格——看起来和「书都没了」一模一样。

已补 `LibraryNoMatch`。

### 1.8 两处数字口径不一致

- **平均进度**：iOS 四舍五入，Android 截断。49.7% 在两台手机上分别显示 50% 和 49%。
  已统一为四舍五入。
- **累计阅读时长**：iOS 会说「1小时30分」和「<1 分钟」；Android 只会说「1 小时」
  （60–119 分钟全部塌缩）和「0 分钟」。iOS 的口径更准，已提升为共用实现
  `JerreaderCopy.readingDuration(totalSeconds:)`，两端调用同一个函数。

### 1.9 相对时间有两份实现

iOS `JerreaderRelativeTime` 和 Android 各有一份「刚刚／N 分钟前／N 小时前／N 天前」。
桶一样，实现两份，没有任何东西保证它们相等。

已收进 `JerreaderCopy.relativeTime(elapsedSeconds:)`；iOS 侧只保留把 `Date`
换算成秒的那几行。`core` 的 `JerreaderCopyTest` 覆盖了全部边界。

### 1.10 学习页

标题和四个分段（翻译／复习／生词本／历史）两端一致；复习标题读 `JerreaderCopy`，
其他既有标题沿用同一来源。Android 的 `LearningTab` 与 iOS 的 `LearningSection` 顺序相同，
窄屏下四项均保留图标和文字，不发生截断。

学习页的大标题同样用 `displaySmall`，所以 §1.2 的字号修复对它一并生效。

### 1.11 设置 → 数据与隐私

Android 分成「本机数据」「写出副本」两组、共 6 条承诺；iOS 是一个平铺列表、只有 3 条。
也就是说同一个 App 在两台手机上**做出的承诺不一样多**——缺的是
「导入的书籍是只读输入」「受 DRM 保护的出版物会被拒绝打开」和整个「写出副本」组。

已把 iOS 改成同样的两组六条。三处点名平台机制的措辞保持各自的说法
（钥匙串 / Android Keystore、IPA / APK、Apple 系统翻译 / Android 本机翻译），
因为换成对方的说法在这一端就是假话。

同时对齐了「支持」组的行序（iOS 的顺序：操作指南 → 备份与恢复 → 数据与隐私），
以及一处措辞（iOS 的「PDF/OCR」→「PDF/文字识别」）。

### 1.12 顺带修掉的一个真 bug

Android 的格式筛选 chip 存的是小写格式名，过滤时做的是大小写敏感比较。
只要某本书的 `sourceFormat` 不是全小写，选中该格式就会得到一个空书架，
而且不会有任何报错。已改为 `equals(ignoreCase = true)`。

### 1.13 1.4 生词状态与词典来源

两端生词本现在使用同一套「待学习／学习中／已掌握／已忽略」状态和相同的筛选顺序。
筛选与导出都放在搜索栏右侧的 42pt/dp 工具按钮中；无匹配状态统一显示
「该状态下没有词条」，不会误报成「收藏还是空的」。搜索占位统一缩短为
「搜索词语或译文」，避免 iPhone 窄屏截断而 Android 完整显示。

Android 原先把状态选择器和收藏星同时塞在词条标题行，长英文词会挤压操作区。
现在状态移到查询次数行，并增加可点开的「词条详情」，与 iOS 一样可以查看全部五条语境；
两端详情中的离线英文解释统一标为「词典释义」，不再误写成「中文释义」。

「设置 → 词典来源」两端显示相同的 JMdict 日期、许可和联网词典说明，项目页与中文
维基词典也都可点开。状态筛选、导出和清空历史按钮补齐了 Android 无障碍说明。

真实资源回归还发现了 JMdict 同形词优先级问题：单字「本」同时是「元（もと）」词条的
异体写法和「本（ほん）」的词头。共用索引现在优先选择查询文字与 lemma 完全相同的词条，
iOS 与 Android 都会返回常见读音「ほん」。

### 1.14 1.4.1 iOS 翻译输入稳定性

iOS 翻译工具不再在输入法组合期间用 SwiftUI 状态覆盖 marked text；连续输入中文、日文或
中日混合文本时，候选确认、字符计数和界面重绘都不会删掉未完成的文字。点击翻译会先提交
候选再读取原文，切换到生词本或历史再返回时也会恢复当前草稿。Android 输入控件没有这条
UIKit/SwiftUI 桥接路径，因此无需复制平台专用实现；两端可见的输入内容与翻译请求语义一致。

### 1.15 1.5 日语复习与可选学习模块

复习的队列分类、日语优先级、挖空提示与四档间隔算法都来自共用
`VocabularyReviewScheduler`。两端卡片按相同顺序展示读音、基本形、词性、活用、前三条释义、
用法和例句；Android 补齐了例句持久化，备份与恢复字段也对齐。

设置页均把「显示学习模块」放在偏好组首项，默认开启。关闭后主导航只保留书架和设置，
不会删除生词或复习进度；重新开启后继续原队列。界面分别在 iPhone 16 Pro（393×852）与
Android 1080×2400 模拟器上检查，四分段、复习问答、评分按钮和显隐状态均无截断。

## 2. 刻意保留的差异

这些不是疏漏，是两边平台本来就不同的地方，**不要**在后续维护中「顺手对齐」。

| 差异 | 原因 |
| --- | --- |
| 阅读引擎（Readium Kotlin toolkit vs swift-toolkit） | 两个原生实现，`core` 只统一它们之上的决策 |
| 翻译后端（ML Kit vs Apple Translation） | 平台各自的端上翻译能力，无法共用 |
| 文件访问（SAF 持久授权 vs security-scoped bookmark） | 两套完全不同的系统授权模型 |
| 数据层（Room vs SwiftData） | 各自平台的持久化方案；`core` 不碰存储 |
| 格式筛选 chip（EPUB／PDF／…） | **仅 Android 有**。iOS 没有对应功能。这是多出来的能力，不是样式不一致，删掉等于减功能 |
| 「从备份恢复」的显示条件 | iOS 只在「这台设备还没装过书」时显示；Android 一直显示。iOS 的判断依赖 SwiftData 的安装痕迹，Android 侧没有等价信号 |

## 3. 桌面显示名已经对齐

**应用在桌面上的名字**：

- Android：英文环境 `Jerreader`，中文环境 **读鼠**（`values-zh-rCN/strings.xml`）。
- iOS：英文环境 `Jerreader`，简体中文环境 **读鼠**（`InfoPlist.xcstrings`）。

两端现在都遵守品牌规则：工程名、包名和应用内文案使用 `Jerreader`，只有简体中文
系统的桌面显示名使用「读鼠」。

## 4. 结构上的结论

真正让两端漂移的不是「有人改错了」，而是**同一个决定在两处各写了一份**。
所以这次除了改具体的像素和文字，更重要的是把「决定」搬进了共用代码：

- 文案 → `core/design/JerreaderCopy.kt`
- 版本号 → `version.properties`（Android 直接读，iOS 经 `syncIosVersion` → `Version.xcconfig`）
- 选区高亮几何、翻译卡定位、跨页展开等算法 → `core/`（本次之前已在）

以后新增任何两端都看得见的文字或数字，先问一句：**这是决定，还是画法？**
是决定就进 `core`。详见 [MAINTENANCE.md](MAINTENANCE.md)。
